## 0. 一页摘要

### 0.1 引擎要解决的两个问题

1. **长期调度**：一个单词下一次应该在哪一天复习？
2. **每日计划**：今天应该学哪些词、各学多少、按什么顺序学、同一个词今天要出现几次？

这两个问题必须分开建模。多数开源 SRS 只解决了第 1 个问题；参考产品真正形成差异的是第 2 个问题——把“复习量”和“新学量”合并成一个每日学习量，并在两者之间动态分配。

### 0.2 五条核心结论

1. **双层结构**：长期调度层负责“哪天再见”，每日计划层负责“今天学什么”。不要把两者压成一个排序器。
2. **当日首次原则**：只有“计划内、且是该词当天第一次出现”的评分，才会改变长期记忆状态；同一天后续出现的评分只影响当天队列；“今日回顾 / 历史回顾”里的评分完全不影响长期规划。【官方】
3. **学习量是总量**：默认 `每日学习量 = 当日复习量 + 当日新学量`，先复习后新学；复习多则新学少，复习少则新学多；复习积压时新学为 0。【官方】
4. **同日重复用队列位置表达**：不需要分钟级定时器。一个词在当天第几个单词之后再次出现，由队列位置决定；长期间隔只按“天”计算。
5. **策略可替换、日志可重放、结果可解释**：引擎定义行为契约与策略接口；参考策略只是其中一种实现；同样的日志重放必须得到同样的状态。

### 0.3 引擎的输出契约（概念级）

| 能力 | 输入 | 输出 |
|---|---|---|
| 评分 | 单词、评分、上下文、时间 | 新的记忆状态、下次到期日、间隔天数、解释 |
| 每日计划 | 当日状态、配置、学习日 | 有序队列（复习 / 新学）、目标数量、分配理由 |
| 预测 | 当前状态、未来天数 | 每日到期量、积压量、压力提示 |
| 统计 | 日志、状态 | 记忆持久度分布、遗忘曲线、每日记录 |
| 解释 | 任意结果 | “为什么是这一天 / 为什么排在这里” |

## 1. 项目背景与边界

### 1.1 两个项目的关系

| 项目 | 定位 | 交付物 |
|---|---|---|
| P1：复习规划引擎 | 通用、平台无关、应用形态无关的核心业务规则 | 本业务描述文档；后续可附一致性测试用例 |
| P2：网页端实现 | 在当前技术环境下应用 P1 的一个完整案例 | Web 应用 |

P1 不直接提供“可运行代码”，而是提供**可被任何语言、任何平台实现的行为契约**。这样做的好处是：十年后 Rust 可能不再流行，但“什么算一次有效复习、复习积压时新学量如何变化”这类业务规则仍然有效。

### 1.2 引擎边界

**引擎负责：**

- 单词 / 词条的身份与记忆规划状态
- 记忆状态（稳定度、难度、到期日等）
- 评分语义与长期调度
- 每日学习量、复习 / 新学分配、排序、会话队列
- 同日重复、完成判定、跳过、结转
- 到期预测、记忆持久度、遗忘曲线等统计
- 复习日志、状态快照、导入导出、确定性重放

**引擎不负责：**

- 单词内容：释义、例句、助记、音频、图片
- 词书版权与词库分发
- UI / UX、动画、手势、主题
- 账号、登录、支付、会员、单词上限售卖
- 社交、排行榜、组队、签到、补签卡
- 推送通知、日历提醒
- 云同步的传输层与冲突合并（引擎只定义数据契约）
- 具体算法参数的生产级训练（引擎定义策略接口与参考策略）

> 边界的原则：**引擎只依赖“单词 ID + 用户行为 + 配置 + 时间”，不依赖单词内容，也不依赖运行平台。**

### 1.3 设计原则

| 原则 | 含义 | 可检验的后果 |
|---|---|---|
| 行为契约优先 | 文档描述“必须发生什么”，不规定语言与架构 | 任何实现都能用同一组场景验收 |
| 确定性 | 相同输入 + 相同日志 + 相同配置 ⇒ 相同结果 | 可以回放、对账、迁移 |
| 机制与策略分离 | 引擎提供流程与不变量；算法是可替换策略 | 可以换算法而不改业务规则 |
| 平台无关 | 不假设有网络、数据库、系统时钟、UI | 可在本地、服务端、嵌入式运行 |
| 可解释 | 每个到期日、每个队列位置都有理由 | 用户能理解“为什么今天学这个” |
| 保守默认 | 默认行为优先保证记忆效果，不隐藏复习债务 | 不把“以后要还的债”伪装成“今天学得多” |
| 内容中立 | 不存储、不解析单词内容 | 可适配任何语言、任何词表 |

### 1.4 非目标

- 不是一套具体算法；不是 FSRS 的封装；不是墨墨的复刻版。
- 不是数据库设计；不是 API 规范；不是 UI 规范。
- 不承诺与参考产品逐像素、逐数值一致；只承诺行为语义可对照。
- 不解决“用户是否真的想学”的动机问题；只保证计划在给定约束下自洽。

### 1.5 调研方法与可信度

本文的信息来源按可信度排序：

1. **官方文档 / 帮助页**：`maimemo.com/help30`、`memodocs.maimemo.com`。用于确定按钮语义、每日学习量、词书关系、熟知 / 删除等规则。
2. **公开论文 / 官方实验报告**：KDD 2022、TKDE 2023、2025 年算法实验报告。用于理解 MM 系列算法的演进、WDR / MMDB / MRL / SSP-MMC 等概念，以及“稳定度 / 难度 / 可提取性”模型。
3. **社区实测 / 截图**：V2EX、小红书、知乎、百度经验、什么值得买等。用于补充官方未文档化的界面行为，例如凌晨 4 点切点、“按规划 / 填满”、70/30 排序、“平衡复习压力”。

处理冲突的原则：

- 官方与社区冲突时，以官方为准；
- 只有社区证据时，写成**可配置项**，并标注【社区】，不写成“官方事实”；
- 官方文档自身存在版本差异时（例如“最长一年”与“最长间隔无固定”），保留差异说明，给出兼容默认值；
- 不把参考产品的私有参数、未公开公式写成确定结论。

| 词条 | Word | 内容层的词；一个 Item 可以引用一个 Word。 |
| 词书 | Book | Item 的一个有序集合，是“视图”，不是记忆状态的拥有者。 |

| 逾期 | Overdue | `dueDay < 今天`，到期未复习。 |
| 新学 | New | Item 从未被学习过，第一次进入学习流程。 |
| 复习 | Review | Item 已有记忆状态，之后再次出现。 |

| 同日重复 | Same-day repeat | 同一个学习日内，Item 第二次及以后出现。 |
| 回顾模式 | Review mode | “今日回顾 / 历史回顾 / 自由回顾”等非计划内学习。 |

| 稳定度 | Stability, S | 记忆强度；在参考策略中，表示“回忆概率降到 90% 所需的天数”。 |

| 可提取性 | Retrievability, R | 当前时刻能回忆起来的概率，0–1。 |

| 复习量 | Review quota, Rq | 当日计划内复习 Item 的数量。 |
| 新学量 | New quota, Nq | 当日计划内新学 Item 的数量。 |
| 计划 | DailyPlan | 某学习日的目标数量与有序队列。 |
| 会话 | Session | 用户从开始学习到完成 / 离开的一次队列执行过程。 |
| 策略 | Policy | 可替换的算法组件，如调度策略、排序策略、分配策略。 |

## 3. 领域模型

### 3.1 调度单元与词书

**ITEM-001**：引擎以 `itemId` 作为唯一身份。`itemId` 必须稳定、可序列化、不依赖数据库自增。

**ITEM-002**：默认以“单词”为调度单元；同一单词在不同词书中共享同一份记忆状态。参考产品明确说明“词库是一个整体，词书只是分类”，同一单词在不同词书中的熟知度、记忆历史、下次复习时间相同。【官方】

**ITEM-003**：可以配置为“单词 + 义项”粒度。此时不同义项是不同 Item，拥有独立记忆状态；引擎不规定如何切分义项，只要求 `itemId` 能唯一标识。

**ITEM-004**：词书只保存 `itemId` 的有序列表与元数据，不得拥有或复制记忆状态。删除词书不得删除记忆状态；切换词书也不得停止已加入规划的 Item 的复习。参考产品明确：所有已加入记忆规划的单词都会按计划持续复习，不会因为切换词书就停止安排。【官方】

**ITEM-005**：引擎可以接收一个可选的 `difficultyPrior`（1–10），用于冷启动时估计单词难度；没有时使用策略默认值。该先验不随词书变化。

### 3.2 记忆规划状态机

一个 Item 在用户维度上的状态：

```
                    select                first scheduled rating
   unselected ──────────────► queued ─────────────────────────► active
        ▲                        │                                │
        │                        │ markKnown                      │ markKnown
        │                        ▼                                ▼
        │                      known ◄────────────────────────── known
        │                        │
        │                        │ unmarkKnown
        │                        ▼
        │                      active
        │
        │ delete                 delete
        └──────── deleted ◄─────────── any state
```

| 状态 | 含义 | 是否进入每日计划 | 是否保留记忆状态 |
|---|---|---|---|
| `unselected` | 未加入记忆规划 | 否 | 无 |
| `queued` | 已加入，但一次都没学过（灰色打勾圆圈） | 是（新学池） | 无 |
| `active` | 已学过，参与长期调度 | 是（复习池） | 有 |
| `known` | 熟知，永久退出 | 否 | 保留（用于统计 / 撤销） |
| `suspended` | 暂停 / 不想背 | 否 | 保留 |
| `deleted` | 已删除，记忆数据清空 | 否 | 无（逻辑墓碑） |

**ENR-001**：`known`、`suspended`、`deleted` 的 Item 不得出现在每日计划、到期预测、复习队列中。

**ENR-002**：`queued` 的 Item 没有记忆状态；第一次计划内评分后才创建 `MemoryState` 并转为 `active`。

**ENR-003**：`delete` 必须清空该 Item 的记忆状态；再次加入时按新词处理。参考产品明确“删除会清空该单词所有记忆数据”。【官方】

**ENR-004**：`suspend` 与 `delete` 不同：暂停保留记忆状态；恢复时默认 `dueDay = max(原 dueDay, 今天)`，避免一恢复就产生大量逾期。该默认可配置为“保留原到期日”。

**ENR-005**：`markKnown` 是用户断言，不是算法自动判定。参考产品将“熟知”定义为“即使不复习也能记住超过 1 年”，但引擎不得仅凭间隔自动标记熟知。【官方】

**ENR-006**：`unmarkKnown` 的行为必须明确：默认恢复标记前的记忆状态快照；若没有快照，则按“重新学习”处理，`dueDay = 明天`。该行为应由配置 `knownUndoPolicy = restore | relearn` 控制。

### 3.3 记忆状态（MemoryState）

| 字段 | 类型 | 说明 |
|---|---|---|
| `itemId` | string | 调度单元 ID |
| `stabilityDays` | number ≥ 0 | 稳定度；参考策略中为“回忆概率降到 90% 的天数” |
| `difficulty` | number 1–10 | 难度 |
| `dueDay` | DayKey | 下次到期日；只精确到天 |
| `lastReviewDay` | DayKey \| null | 上次“计划内首次评分”的学习日 |
| `phase` | enum | `new / learning / review / relearning`；用于展示与策略，不强制状态机 |
| `reps` | integer ≥ 0 | 计划内评分次数（不含同日重复、回顾模式） |
| `lapses` | integer ≥ 0 | 评为“忘记”的次数 |
| `firstLearnedDay` | DayKey \| null | 第一次学习日 |
| `lastRating` | enum \| null | 最近一次长期评分的评分 |
| `lastIntervalDays` | integer \| null | 最近一次安排的间隔 |
| `knownAt` | timestamp \| null | 标记熟知的时间 |
| `version` | integer | 乐观并发版本 |

**STATE-001**：`dueDay`、`lastReviewDay` 必须是 DayKey（整数天），不得存“某日 14:30”这种时刻；同日重复不写 `dueDay`。

**STATE-002**：`stabilityDays` 与 `difficulty` 的语义由策略定义；引擎只要求它们可序列化、可解释、可版本化。

**STATE-003**：状态快照可以丢失，但只要能拿到完整日志，就必须能重建到相同状态。

### 3.4 复习日志（ReviewLog）

日志是不可变事实，不是“可覆盖的状态”。

| 字段 | 说明 |
|---|---|
| `eventId` | 全局唯一；用于幂等 |
| `userId` | 用户 |
| `itemId` | 调度单元 |
| `at` | UTC 时间戳（ISO 8601） |
| `dayKey` | 该事件归属的学习日 |
| `timezone` | 事件发生时的 IANA 时区 |
| `context` | `scheduled` / `same_day_repeat` / `today_review` / `history_review` / `free_review` / `extra` |
| `rating` | `know` / `vague` / `forgot` / `known` |
| `elapsedDays` | 距上次计划内评分的实际天数；首次为 null |
| `scheduledIntervalDays` | 上次安排的间隔；用于对照，不参与状态更新 |
| `stateBefore` / `stateAfter` | 快照或引用；便于审计 |
| `intervalAfter` | 本次安排的天数 |
| `queueAppearance` | 当天第几次出现（1 起） |
| `sessionId` / `planId` | 会话与计划 |
| `policyId` / `policyVersion` / `paramsHash` | 策略版本 |
| `responseMs` | 可选，客户端上报的响应时间 |
| `clientId` | 可选，设备标识（不含 PII） |

**LOG-001**：任何评分都必须写日志，包括不影响长期状态的回顾模式评分。

**LOG-002**：日志一旦写入不得修改；更正只能追加“修正事件”，并在导出时标注。

**LOG-003**：日志必须能区分“计划内”和“非计划内”，否则无法正确重放。

### 3.5 每日计划（DailyPlan）与会话（Session）

**DailyPlan**

| 字段 | 说明 |
|---|---|
| `planId` | 计划 ID |
| `userId` / `dayKey` | 归属 |
| `generatedAt` | 生成时间 |
| `configHash` | 生成时的配置指纹 |
| `mode` | `merged` / `split` |
| `targets` | `{ total, review, new }` |
| `reviewItems` / `newItems` | 有序的 item 引用 |
| `status` | `active / completed / superseded` |
| `version` | 计划版本；配置变更时递增 |

**Session**

| 字段 | 说明 |
|---|---|
| `sessionId` | 会话 ID |
| `planId` | 所属计划 |
| `queue` | 当前有序队列（item + role + appearance） |
| `cursor` | 当前位置 |
| `appearances` | 每个 item 当天已出现次数 |
| `status` | `active / paused / completed / closed` |
| `startedAt` / `closedAt` | 时间 |

**PLAN-001**：计划是“当日快照”，不是永久事实；跨天后必须重新生成。

**PLAN-002**：计划中可以包含未开始的 Item；已完成的 Item 不因计划重算而回退。

**PLAN-003**：会话队列必须能从“计划 + 日志 + 配置”重建；允许保存快照以加速恢复，但快照不得成为唯一真相。

### 3.6 配置（EngineConfig）

| 配置项 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `dailyStudyAmount` | int ≥ 0 | 100 | 每日学习量目标（合并模式的总量） |
| `volumeMode` | `merged` / `split` | `merged` | 复习量与新学量是否合并 |
| `dailyReviewQuota` | int ≥ 0 | — | 分开模式下的复习量 |
| `dailyNewQuota` | int ≥ 0 | — | 分开模式下的新学量 |
| `reviewFillMode` | `by_plan` / `fill` | `by_plan` | 只复习到期词，还是提前复习填满 |
| `studyOrder` | `review_first` / `new_first` / `shuffled` | `review_first` | 复习与新学的先后 |
| `reviewOrder` | `risk` / `balanced` / `reference_70_30` / `custom` | `risk` | 复习排序策略 |
| `newOrder` | `book` / `random` / `frequency` / `priority` | `book` | 新学排序 |
| `allowVagueComplete` | bool | `false` | “模糊”是否算完成当天复习 |
| `maxIntervalDays` | int | 365 | 长期间隔上限 |
| `minIntervalDays` | int | 1 | 长期间隔下限 |
| `forgotNextDay` | bool | `true` | “忘记”是否固定次日到期 |
| `sameDayGap` | int | 5 | 同日重复间隔几个单词后出现；0 表示队尾 |
| `maxAppearancesPerDay` | int \| null | null | 单日最多出现次数；null 为不限制 |
| `vagueMaxIntervalDays` | int \| null | null | “模糊”后长期间隔的上限；null 表示由策略决定 |
| `newWordsBlockedByBacklog` | bool | false | 分开模式下，复习池超过配额时是否阻断新学 |
| `resumeDuePolicy` | `keep` / `today` / `max` | `max` | 暂停恢复时的到期日处理 |
| `targetRetention` | number 0–1 | 0.9 | 目标保留率（策略参数） |
| `dayCutoffMinutes` | int 0–720 | 240 | 跨天切点，默认 04:00 |
| `timezone` | IANA string | 系统时区 | 学习日计算时区 |
| `pressureBalance` | `off` / `reserve_new` / `spread_backlog` | `off` | 复习压力平衡策略 |
| `newReserveRatio` | number 0–1 | 0.2 | 积压时为新学保留的比例 |
| `maxNewPerDay` | int \| null | null | 新学量硬上限（策略层） |
| `overdueCapDays` | int \| null | null | 逾期计入策略输入的上限；null 为不封顶 |
| `knownUndoPolicy` | `restore` / `relearn` | `restore` | 取消熟知后的处理 |
| `planHorizonDays` | int | 30 | 预测天数 |
| `policyId` / `policyVersion` | string | 参考策略 | 策略标识 |
| `policyParams` | JSON | 策略默认 | 策略参数 |

**CFG-001**：配置变更必须写 `settings_changed` 事件；计划按新配置重算未开始部分。

**CFG-002**：配置必须可导出、可版本化；不得把关键行为藏在不可见的服务端开关里。

**CFG-003**：默认值应尽量贴近参考产品的可见行为；但每个默认值都必须可改，并在文档中说明其影响。

### 3.7 时间模型

**TIME-001**：引擎内部只使用两种时间：UTC 时间戳（日志）与 DayKey（调度）。所有长期调度按天计算，不按小时。

**TIME-002**：DayKey 的计算方式：

```
若 本地时间 < dayCutoff：
    dayKey = 本地日历日期 - 1 天
否则：
    dayKey = 本地日历日期
```

例如切点为 04:00：某日 02:00 属于前一天；04:00 起属于新一天。

**TIME-003**：DayKey 必须是整数（如“距 1970-01-01 的天数”），不得使用本地化字符串作为主键。

**TIME-004**：`elapsedDays = 今天 - lastReviewDay`，按日历天计算，不按 24 小时毫秒数计算；跨夏令时也按日历天。

## 4. 长期调度：一个单词下一次哪天出现

### 4.1 最重要的规则：当日首次、计划内

**SCH-001**：只有同时满足以下条件的评分，才会更新长期记忆状态：

1. `context = scheduled`（计划内学习 / 复习，包含用户主动追加的新词）；
2. 该 Item 在该学习日内，之前没有任何 `scheduled` 评分。

**SCH-002**：同一天内第二次及以后出现的评分，无论点“认识 / 模糊 / 忘记”，都**不得**改变 `dueDay`、`stabilityDays`、`difficulty`、`reps`、`lapses`，只影响当天队列。

**SCH-003**：`today_review`、`history_review`、`free_review` 上下文的评分，无论是否当天第一次，都**不得**改变长期状态。参考产品明确：“今日回顾”和“历史回顾”的所有记忆反馈都不会影响单词未来在第几天出现。【官方】

**SCH-004**：如果一个到期词先在“历史回顾”里被评分，之后又出现在计划内，计划内的评分仍然是该词当天的“首次计划内评分”，应当更新长期状态；回顾模式的那次评分只写日志。

**SCH-005**：同一个 Item 在同一个学习日内，最多只能有一次长期状态更新；重复提交同一 `eventId` 必须幂等，不得重复计算。

**SCH-006**：如果当天没有计划内评分（用户没学），则状态不变，`dueDay` 保持原值；第二天它自然成为逾期词。

> 这条规则是整套引擎最容易被实现错的地方。很多 SRS 会把同一天内的每次评分都拿来更新稳定度，导致“越复习越记不住”或“同一天点两次认识，间隔翻倍”。参考产品的语义是：**一天只认第一次。**

### 4.2 四类操作的语义

| 操作 | 用户含义 | 长期影响 | 当日队列 | 统计归类 |
|---|---|---|---|---|
| 认识 `know` | 发音、拼写、释义能迅速回忆 | 稳定度上升；`dueDay = 今天 + I`，`I ≥ 1` | 当天不再出现（除非被其他规则重新加入） | 复习成功 / 新学成功 |
| 模糊 `vague` | 发音略错、拼写错几个字母、释义“好像知道但说不清” | 稳定度小幅上升或不变；`dueDay = 今天 + 短间隔` | 当天至少再出现 1 次 | 复习困难 / 新学困难 |
| 忘记 `forgot` | 音、形、义完全没印象 | 稳定度下降或重置；默认 `dueDay = 明天` | 当天至少出现 2 次（首次 + 至少 1 次重复） | 复习失败 / 新学失败；`lapses + 1` |
| 熟知 `known` | 确定已经记牢 | 终止调度，不再有 `dueDay` | 立即移出队列 | 熟知 |

**SCH-007**：“认识”不等于“永远记住”。参考产品明确算法中没有“完全记住”的概念，间隔会越来越长但不会停止，直到用户标记“熟知”。【官方】

**SCH-008**：“熟知”是**终止动作**，不是第四档评分。默认不得把“熟知”映射成调度评分中的“简单 / Easy”；如果某个策略需要四档评分，可以由适配层把“熟知”映射为 Easy，但必须同时执行终止语义。

**SCH-009**：“忘记”后的次日到期是参考产品的可见行为（“极大概率第二天再次出现”）。【官方】引擎默认用确定性的“次日”实现它，以保证可测试；配置 `forgotNextDay = false` 时才交给策略计算。

**SCH-010**：“模糊”的长期间隔通常较短（1 天或几天），但具体由策略决定；引擎不得把“模糊”当成“认识”的轻微版本而给出长间隔。

> 计数口径：`lapses` 只统计“计划内首次评分为忘记”的长期失败，不统计同日重复时的忘记；每日统计中的“忘记次数”则应统计所有上下文的所有评分。两者不要混用。

### 4.3 同日重复规则

同日重复不是“再次调度”，而是“队列控制”。

**QUEUE-001**：一个 Item 当天第一次出现并评分后，按评分决定是否重新入队：

| 首次评分 | 是否重新入队 | 最少当天出现次数 |
|---|---|---|
| 认识 | 否 | 1 |
| 模糊 | 是 | 2 |
| 忘记 | 是 | 2 |
| 熟知 | 否（终止） | 1 |

**QUEUE-002**：重新入队的位置由 `sameDayGap` 决定：在当前队列中往后数 `sameDayGap` 个 Item 后插入；若剩余不足，则放到队尾；若队列已空，则立即再次出现。

**QUEUE-003**：重复出现时的评分只影响“是否继续留在队列”，不改变长期状态。即使重复时点了“认识”，长期 `dueDay` 仍由当天第一次评分决定。

**QUEUE-004**：完成当天复习的判定：

- 默认 `allowVagueComplete = false`：只有“认识”或“熟知”能让该 Item 完成当天复习；“模糊”“忘记”都会继续留在队列。
- 若 `allowVagueComplete = true`：“模糊”也可以完成当天复习；“忘记”仍然不能完成。
- “完成”只表示“当天不再要求出现”，不表示“记住”。

**QUEUE-005**：`maxAppearancesPerDay` 默认不限制。若配置了上限，达到上限后必须记录 `forced_complete` 事件，并把该 Item 视为“当天完成但未掌握”；策略应给它更短的长期间隔。该机制用于防止极端情况下队列无法结束，不应作为默认行为。

**QUEUE-006**：用户主动“跳过”某个 Item 时，写 `skipped` 事件；复习词保持到期，新词保持未学；跳过不改变长期状态。

### 4.4 下次到期日的计算

**SCHED-001**：对一次有效的长期评分，策略返回 `intervalDays`：

```
intervalDays = clamp(round(policy.nextInterval(state, rating)), minIntervalDays, maxIntervalDays)
dueDay = dayKey + intervalDays
```

**SCHED-002**：`minIntervalDays` 默认 1；不允许出现“认识后当天再次长期到期”的情况。同日重复由队列负责，不由 `dueDay` 负责。

**SCHED-003**：`maxIntervalDays` 默认 365。参考产品帮助页写“最长一年”；其新版文档又写“最长间隔无固定”。【官方】本文取 365 作为兼容默认值，并允许配置为更大的值（例如 36500）。

**SCHED-004**：对“忘记”，默认直接 `dueDay = dayKey + 1`，不经过策略的间隔计算；但策略仍负责更新稳定度 / 难度。这样既符合参考产品的可见行为，也保证“忘记后次日必复习”可测试。

**SCHED-005**：对“模糊”，默认使用策略计算的间隔；若策略给出的间隔超过 `vagueMaxIntervalDays`（可选配置，默认 null），则截断到该值。参考产品的可见描述是“1 天或几天”，不应出现长间隔。

**SCHED-006**：所有取整必须明确规则（默认四舍五入到最近整数）；策略版本必须固定取整方式，避免同一日志在不同实现中产生不同日期。

### 4.5 逾期处理

**SCHED-007**：`dueDay < 今天` 的 Item 进入复习池，优先级按“遗忘风险”处理，而不是按原计划日期简单排队。

**SCHED-008**：计算新的记忆状态时，`elapsedDays` 必须使用**实际经过的日历天**（`今天 - lastReviewDay`），不得使用“原计划间隔”。这是一个常见 bug：安排 71 天、实际 583 天后才复习，却按 71 天更新状态，会严重高估记忆水平。

**SCHED-009**：`overdueCapDays` 只用于限制传给策略的 `elapsedDays` 上限，日志中仍记录真实值；默认 null（不封顶）。设置上限时必须在解释中注明“已截断”。

**SCHED-010**：逾期不产生额外惩罚状态；惩罚应体现在策略对低可提取性的处理上，而不是业务层偷偷扣分。

### 4.6 新词、熟知、删除、暂停

**NEW-001**：新词第一次进入计划时，`phase = new`，没有 `stabilityDays` / `difficulty` / `dueDay`。

**NEW-002**：新词第一次计划内评分后，策略必须给出初始稳定度与难度；`reps = 1`，`firstLearnedDay = dayKey`，`phase = review`（或 `learning`，由策略决定），并计算 `dueDay`。

**NEW-003**：新词当天被评“忘记”后，仍然只算一次“新学”；同一天的重复不重复计入新学数量。

**KNOWN-001**：标记熟知后，`phase = known`，清除 `dueDay`；保留历史状态用于统计和撤销。

**KNOWN-002**：熟知词不计入到期预测、复习量、新学量；可以在“已学列表”中单独统计。

**DELETE-001**：删除是逻辑删除；记忆状态清空；日志保留为审计记录（除非用户请求彻底清除）。再次加入时按 `queued` 处理。

**SUSPEND-001**：暂停词不进入计划；恢复时默认 `dueDay = max(原 dueDay, 今天)`。

### 4.7 不变量

| 编号 | 不变量 |
|---|---|
| INV-001 | 同一个 Item 在同一个学习日内，长期状态最多更新一次 |
| INV-002 | `known` / `suspended` / `deleted` 的 Item 不出现在计划与预测中 |
| INV-003 | `dueDay` 是 DayKey，不含时刻 |
| INV-004 | 有效长期评分后，`dueDay > dayKey`（熟知除外） |
| INV-005 | 同一天内的重复评分不改变 `dueDay` |
| INV-006 | 新词在首次评分前没有 `dueDay` |
| INV-007 | 相同日志 + 相同配置 + 相同策略版本 ⇒ 相同状态 |
| INV-008 | 任何计划外评分都不改变长期状态 |

## 5. 每日计划：今天学什么、学多少、什么顺序

### 5.1 学习量的定义

**PLAN-010**：默认（合并模式）：

```
每日学习量 N = 当日复习量 Rq + 当日新学量 Nq
```

N 是**目标**，不是硬上限。用户完成计划后仍可主动追加学习；追加不受 N 限制，但会增加未来的复习负担。【官方】

**PLAN-011**：N 本质上是“每天愿意投入多少时间”的代理。引擎按“Item 数”计算；应用层可以用平均耗时把分钟映射为数量，但引擎不负责测量时间。

**PLAN-012**：参考产品不推荐把“每日复习量”和“每日新学量”分开固定，因为固定新学量会让复习量持续累积。【官方】因此：

- 合并模式是默认；
- 分开模式必须可用，但应用应显示“复习债务”提示；
- 引擎不得在用户不知情的情况下把固定新学量当作可持续策略。

### 5.2 计划生成流程

在每天第一次打开应用（或跨天切点之后）生成计划：

```
1. 计算 dayKey
2. 取状态快照
3. reviewPool = 所有 active 且 dueDay <= dayKey 的 Item（按复习排序策略排序）
4. futurePool = 所有 active 且 dueDay > dayKey 的 Item（按 dueDay 升序）
5. 计算 reviewTarget / newTarget
6. 从 reviewPool 取前 reviewTarget 个；若 fill 模式不足，则从 futurePool 提前取
7. 从 newPool 取前 newTarget 个
8. 按 studyOrder 组合成队列
9. 持久化 DailyPlan，记录分配理由
```

**PLAN-013**：复习池必须包含所有逾期 Item；不得因为“超过今日学习量”而把逾期 Item 从池中删除，它们只是没被今天选中。

**PLAN-014**：默认顺序是“先复习，再新学”。参考产品明确默认先复习后新学，复习顺序按遗忘程度从高到低。【官方】

**PLAN-015**：合并模式下：

```
actualReview = min(|reviewPool|, N)          // by_plan
newTarget   = min(|newPool|, max(0, N - actualReview), maxNewPerDay ?? +∞)
```

**PLAN-016**：如果 `|reviewPool| >= N`，则 `newTarget = 0`。这正是“复习多时少学新词”的极端情况；除非启用压力平衡策略，否则不得强行插入新词。

**PLAN-017**：分开模式下：

```
reviewTarget = min(|reviewPool|, dailyReviewQuota)
newTarget    = min(|newPool|, dailyNewQuota)
```

两者独立；总学习量约为两者之和，可能超过 `dailyStudyAmount`。应用应明确展示这一点。

**PLAN-018**：`reviewFillMode = fill` 时，如果到期复习不足 `reviewTarget`，允许从 `futurePool` 按 dueDay 升序提前取词填满；必须：

- 在计划中标记 `advanced = true`；
- 在评分时按“提前复习”处理（实际 elapsed 小于原间隔）；
- 向用户显示“此操作会改变这些词的下次到期日”的警告。

参考产品把“填满”描述为“当日应复习以外的单词将提前至今日复习规划里，此操作不可撤回”。【社区】

**PLAN-019**：计划一旦生成，在当天保持稳定；只有以下情况触发重算：

- 用户修改学习量 / 模式 / 排序；
- 用户追加新词；
- 用户标记熟知 / 删除 / 暂停；
- 跨天。

重算只影响未开始的 Item；已完成 Item 不回退。

**PLAN-020**：计划必须暴露分配理由，例如：

```json
{
  "total": 100,
  "reviewTarget": 80,
  "newTarget": 20,
  "reason": "到期复习 80 个，未超过每日学习量 100，剩余 20 个名额分配给新词"
}
```

### 5.3 合并模式与分开模式

| 维度 | 合并模式（默认） | 分开模式 |
|---|---|---|
| 用户设置 | 一个总数 N | 复习量 R、新学量 M |
| 新学量 | `N - 实际复习量`，动态 | 固定 M |
| 复习积压时 | 新学自动降为 0 | 新学仍按 M 执行（可配置阻断） |
| 优点 | 每日总压力平稳；不容易突然爆炸 | 新学进度可预测 |
| 风险 | 复习多时新学几乎停滞 | 复习债务持续累积 |
| 适用 | 长期备考、时间固定 | 短期冲刺、明确想推进新词 |

**PLAN-021**：分开模式应提供可选开关 `newWordsBlockedByBacklog`：开启时，若复习池超过复习配额，则新学量为 0；关闭时，新旧独立。默认关闭，并在 UI 提示风险。

### 5.4 复习排序策略

**ORDER-001**：默认 `risk`：按当前可提取性 `R` 从低到高排序（即遗忘风险从高到低）；`R` 相同时按 `dueDay` 更早、`difficulty` 更高、`stabilityDays` 更低、`itemId` 字典序稳定排序。

**ORDER-002**：`balanced`：先按风险排序，再把高风险与低风险交错排列，避免连续出现大量难词造成疲劳。具体交错算法由策略定义，但必须确定性。

**ORDER-003**：`reference_70_30`：70% 的复习词按风险排序，30% 从剩余词中随机抽取，再按种子打乱。该策略来自社区对参考产品的观察（“记忆效率优先”约 70% 按间隔、30% 随机）。【社区】默认不启用，仅作为兼容选项。

**ORDER-004**：`custom`：应用可注入比较器；引擎必须校验比较器不修改状态、不依赖随机（除非提供种子）。

**ORDER-005**：排序必须稳定、可解释；每个 Item 的位置应能回答“为什么它排在这里”。

### 5.5 新学排序策略

**ORDER-006**：`book`：按词书内的顺序；`random`：按 `hash(userId, dayKey, planVersion)` 作为种子随机；`frequency`：按词频 / 优先级；`priority`：按用户自定义优先级。

**ORDER-007**：随机必须使用可复现的种子，不得使用系统随机数；同一天重算计划应得到相同顺序（除非配置或词池变化）。

### 5.6 复习压力平衡

**PRESSURE-001**：`off`：严格复习优先；复习积压时新学为 0；积压自然逐日消化。

**PRESSURE-002**：`reserve_new`：即使复习积压，也为新学保留 `newReserveRatio × N` 的名额；复习目标相应减少。该策略适合“长期不学新词会失去动力”的场景，但会延长积压消化时间。参考产品的“平衡复习压力”允许用户在大量积压时继续学新词。【社区】

**PRESSURE-003**：`spread_backlog`：把逾期 Item 按“每日最多复习量”分摊到未来若干天。实现方式必须是显式的 `defer` 事件：只改 `dueDay`，不改记忆状态；必须记录审计，并向用户说明“这会推迟复习，可能降低保留率”。

**PRESSURE-004**：任何压力平衡策略都不得伪造“已完成复习”；未复习就是未复习，只是计划层面延后。

**PRESSURE-005**：引擎应提供“可持续新学量”可选策略：用参考策略模拟未来 H 天的复习量，选择最大的 k，使得加入 k 个新词后未来每日复习量不超过 N（或不超过 N 的某个倍数）。该策略比“余量法”更能避免复习债务，但计算量更大，默认不作为参考行为。

### 5.7 计划中途变更

| 变更 | 行为 |
|---|---|
| 增大 N | 从未开始的池中追加 Item；优先补复习，再补新学 |
| 减小 N | 不取消已完成；从未开始的队尾裁剪；新学目标重新计算 |
| 合并 ↔ 分开 | 重算目标；未开始队列重建；已完成保留 |
| 修改排序 | 只重排未开始部分；当前 Item 不跳变 |
| 追加新词 | 若计划未完成，追加到新学队尾；若已完成，进入 `extra` 模式，不受 N 限制 |
| 标记熟知 / 删除 / 暂停 | 从队列移除；写事件；不改变其他 Item 的状态 |
| 跨天 | 关闭会话；未完成 Item 保持到期；生成新计划 |

**PLAN-022**：每次重算必须递增 `plan.version`，并记录 `replan_reason`；会话游标按 `itemId` 保留，不得按数组下标保留。

**PLAN-023**：减小 N 时，已经开始的 Item 不因“超出新目标”而被中断；否则用户会感到“学到一半被抢走”。

### 5.8 完成、跳过与结转

**PLAN-024**：计划完成的条件是：所有计划内 Item 都处于“已完成”或“已跳过”状态。仅有“复习完成”不算完成，除非新学目标为 0。

**PLAN-025**：`skip` 是显式行为：复习词保持到期，新词保持未学；写日志；不计入完成数量；不改变长期状态。

**PLAN-026**：跨天时，未完成的复习词自然成为逾期；未完成的新词仍在 `queued` 池；不产生“断签惩罚”之类的业务规则（签到属于应用层，不属于引擎）。

**PLAN-027**：同一天内，已经完成的 Item 再次被用户主动打开，进入 `same_day_repeat` 或 `free_review` 上下文，不改变长期状态。

### 5.9 边界情况

| 情况 | 期望行为 |
|---|---|
| 没有到期词，也没有新词 | 计划为空；状态为完成；不报错 |
| 到期词多于 N | 只取 N 个；其余保留到期；新学为 0 |
| 新词少于目标 | 新学取实际可用量；总学习量小于 N；不强行用复习填满（除非 fill） |
| 所有新词都已熟知 | 新学池为空；计划只含复习 |
| N = 0 | 计划为空；不自动学习 |
| 用户未完成计划 | 不惩罚；次日按逾期处理 |
| 同一个词同时出现在复习池和新学池 | 不可能；状态互斥；若数据损坏，以 `active` 优先并报警 |
| 策略返回非法间隔（0、负数、NaN） | 引擎必须拒绝并回退到安全值（1 天）；记录错误 |
| 状态与日志不一致 | 以日志重放为准；快照可重建 |
| 时区变更 | 见第 9 节；不追溯修改历史 DayKey |

## 6. 统计与可解释性

### 6.1 到期预测

**STAT-001**：预测未来 `planHorizonDays` 天内每天的到期数量；今天之前的到期词合并为“逾期”桶，不摊到未来。

**STAT-002**：预测必须排除 `known` / `suspended` / `deleted`；必须区分“复习到期”和“新学待学”。

**STAT-003**：预测是“按当前状态不变”的静态预测；不模拟用户未来评分带来的新到期。若要做动态模拟，必须单独标注“模拟值”。

**STAT-004**：预测应提供压力提示：例如“明天到期 320 个，超过学习量 200”。

### 6.2 记忆持久度

**STAT-005**：记忆持久度定义为“单词当前安排的复习间隔”，即 `dueDay - lastReviewDay`。参考产品的定义是“反映了单词当前安排的复习间隔，记忆持久度越高，遗忘得越慢，规划的间隔越长”。【官方】

**STAT-006**：统计口径默认按阈值分组：`>10 天`、`>30 天`、`>60 天`、`>90 天`；输出每个区间的数量与占比。

**STAT-007**：新词（无间隔）与熟知词单独统计，不混入“持久度 > 10 天”的分子/分母；否则会虚高。

**STAT-008**：如果策略使用稳定度 `S` 而不是间隔，必须在统计口径中明确写“按稳定度”，不得与“按间隔”混用。

### 6.3 熟知度与饼图

参考产品有两个容易混淆的展示：

1. **熟知度**：用于“已学列表按熟知度排序”，官方描述是“离下次复习日期越久，遗忘概率越低，熟知度越高”。【官方】它反映的是“这个词的复习节奏有多长”，不是“现在还记得多少”。
2. **饼图 / 记忆倒计时**：随时间的推移逐渐变成红色空心圈，完全空心时安排复习。【官方】它反映的是“距离到期还剩多少”。

**STAT-009**：引擎应分别提供两个派生指标，不得混为一个：

- `familiarity`：随 `stabilityDays` 或 `intervalDays` 单调递增；默认可用 `intervalDays / (intervalDays + 30)` 归一化到 0–1。具体公式由策略提供，但必须单调。
- `remainingRatio`：`1 - elapsedDays / intervalDays`，clamp 到 0–1；到期时为 0；用于饼图倒计时。

**STAT-010**：`familiarity` 只用于排序和展示，不得反向影响调度；调度只依赖 `MemoryState`。

### 6.4 遗忘曲线

**STAT-011**：遗忘曲线应基于“计划内首次评分”的日志计算，排除同日重复、回顾模式、新词首次学习（或单独分组）。

**STAT-012**：按 `elapsedDays` 分桶，计算每个桶的实际回忆率（认识 / (认识 + 模糊 + 忘记)）；样本不足的桶必须标注“样本不足”，不得画成确定曲线。

**STAT-013**：可以同时展示预测保留率与实际保留率，用于校准；但预测曲线必须注明策略版本。

### 6.5 每日记录

**STAT-014**：每日统计至少包含：新学数、复习数、认识 / 模糊 / 忘记 / 熟知数、完成数、跳过数、逾期数、学习时长（若客户端上报）。

**STAT-015**：统计必须可按学习日聚合，且与日志可对账；不允许出现“统计说复习了 100，日志只有 80”的情况。

### 6.6 解释对象

**EXPLAIN-001**：每个 Item 的调度结果应包含：

```json
{
  "itemId": "w:apple",
  "dueDay": 20456,
  "intervalDays": 12,
  "retrievability": 0.87,
  "stabilityDays": 34.2,
  "difficulty": 5.1,
  "reason": "上次评分‘认识’，稳定度 34.2 天，目标保留率 0.9，计算间隔 12 天"
}
```

**EXPLAIN-002**：每个计划位置应包含排序理由：

```json
{
  "itemId": "w:apple",
  "position": 3,
  "reason": "逾期 4 天，可提取性 0.62，按遗忘风险优先"
}
```

**EXPLAIN-003**：解释必须是“可读的”，不能只返回一串模型权重；至少包含：用了哪个策略、关键输入、最终间隔、是否被边界截断。

## 7. 策略接口

> **先分清三层，避免把“模型”和“实现”并列：**
>
> | 层级 | 内容 | 例子 |
> |---|---|---|
> | 产品策略层 | 每日学习量、先复习后新学、当日首次、同日队列、压力平衡 | 本引擎的核心业务规则 |
> | 调度层 | 根据记忆状态决定“下次间隔多少天” | FSRS 公式、SSP-MMC 最短路、MMDB 查表 |
> | 记忆模型层 | 用哪些变量描述记忆、它们如何随时间变化 | DSR（难度 / 稳定度 / 可提取性）、DHP（难度 / 半衰期 / 回忆概率） |
>
> **DSR 是模型层，不是与 FSRS、MM 并列的第三种算法。** FSRS 是 DSR 的一种公开实现；MM 是墨墨基于同类思想（DHP）的私有实现。D1 选的是“调度层用哪套参考实现”，不是“选模型还是选算法”。

### 7.2 SchedulingPolicy

职责：根据记忆状态与评分，计算新的稳定度、难度、间隔。

| 方法（概念） | 输入 | 输出 |
|---|---|---|
| `initialState` | Item、首次评分、时间 | 初始 `stabilityDays`、`difficulty`、`phase` |
| `review` | 当前状态、评分、实际 elapsed、时间 | 新状态、`intervalDays` |
| `retrievability` | 状态、时间 | 0–1 的 R |
| `describe` | 状态 | 可读解释 |

**POLICY-001**：策略必须是纯函数式的（或至少可重放）：相同输入不得依赖隐藏的全局状态、系统时间、随机数。

**POLICY-002**：策略不得直接读写存储；所有输入通过参数传入。

**POLICY-003**：策略返回的 `intervalDays` 必须经过引擎的边界校验（最小值、最大值、NaN、无穷大）。

### 7.3 DailyPlannerPolicy

职责：在给定池子、配置、历史压力下，决定复习量、新学量、排序。

| 方法（概念） | 输入 | 输出 |
|---|---|---|
| `allocate` | 复习池、新学池、配置、预测 | `reviewTarget`、`newTarget`、理由 |
| `orderReviews` | 复习池、配置 | 有序列表 |
| `orderNew` | 新学池、配置 | 有序列表 |
| `balance` | 积压量、配置 | 是否保留新学名额、是否延后 |

**POLICY-004**：分配策略可以替换（余量法、固定法、可持续法），但必须遵守 §5 的不变量：默认复习优先、新学不超余量、积压不隐藏。

### 7.4 参考策略 R1

**POLICY-005**：本文建议的参考策略是 **DSR 系列（FSRS-3 风格）**，原因：

- 公开、可解释、有 MIT 许可的实现；
- 与参考产品同属“稳定度 / 难度 / 可提取性”家族；
- 足以验证引擎的业务规则，不依赖参考产品的私有数据。

参考策略的核心：

```
R(t) = 0.9 ^ (t / S)
I = round(S * ln(targetRetention) / ln(0.9))
```

其中 `S` 为稳定度（天），`targetRetention` 默认 0.9。评分映射：

| 引擎评分 | 参考策略 grade |
|---|---|
| 忘记 `forgot` | 1（Again） |
| 模糊 `vague` | 2（Hard） |
| 认识 `know` | 3（Good） |
| 熟知 `known` | 终止动作，不进入公式 |

**POLICY-006**：参考策略的初始稳定度、难度更新、失败后稳定度等公式，应采用所选 FSRS 版本的公开公式与默认参数；本文不复制具体参数表，以免版本漂移。实现方必须在 `policyVersion` 中固定公式版本。

**POLICY-007**：参考产品使用半衰期 `h` 与 `p = 2^(-Δt/h)`，FSRS 使用 `R = 0.9^(t/S)`；两者是同一类指数遗忘模型的不同参数化。本文选择 FSRS 参数化是为了复用公开生态，不代表参考产品的内部实现。

**POLICY-008**：参考产品还有“单词难度排名（WDR）”“用户记忆召回水平（MRL）”等个性化维度。【论文】参考策略可以用以下方式近似：

- `difficultyPrior`：外部传入的单词难度 1–10，作为初始难度；
- `userAbility`：可选的用户能力参数，调整初始稳定度或目标保留率；
- 没有数据时使用默认值，不阻塞引擎运行。

**POLICY-009**：参考策略必须支持“目标保留率”可配置。参考产品的记忆卡 MMX-5 使用 0.85；背单词产品未公开其当前值。【论文】【社区】本文默认 0.9，应用可按用户目标调整。

### 7.5 策略版本与迁移

**POLICY-010**：每条日志必须记录 `policyId`、`policyVersion`、`paramsHash`；否则无法解释历史结果。

**POLICY-011**：升级策略不得重写历史日志；只影响升级后的评分。已安排的 `dueDay` 可以选择：

- 保持原样（默认，最稳定）；
- 按新策略重算未来到期（必须显式迁移，并记录 `policy_migrated` 事件）。

**POLICY-012**：策略迁移必须可回滚；回滚不得丢失日志。

### 8.4 导入 / 导出

**DATA-001**：必须支持导出完整状态 + 日志 + 配置 + 策略元数据；导出格式必须有 `schemaVersion`。

- `itemId` 不重复；
- 状态与日志可重放一致（或明确标记“仅导入状态，不导入日志”）；

### 8.5 幂等与并发

**DATA-005**：每个写命令必须带 `commandId`；重复提交返回第一次的结果，不重复写日志。

**DATA-006**：更新 `Enrollment` 必须带 `expectedVersion`；版本冲突时拒绝写入，由调用方重试或合并。

**DATA-007**：同一用户同一学习日默认单写者；多设备并发时，以事件日志为准，状态快照可重建。

**DATA-008**：日志追加必须原子；不得出现“状态更新了但日志没写”或相反。

## 9. 时间语义

### 9.1 学习日与跨天切点

**TIME-005**：默认切点为本地时间 04:00。该值来自社区对参考产品的观察（凌晨 4 点前算前一天），并非官方公开文档的明确承诺。【社区】因此必须可配置，且应用应允许用户改为 00:00。

**TIME-006**：切点只影响 DayKey，不影响日志的 UTC 时间戳；同一事件在导出后仍可还原到正确的学习日。

**TIME-007**：切点变更不得追溯修改历史 DayKey；从变更时刻起使用新切点，并写 `settings_changed`。

### 9.2 时区与夏令时

**TIME-008**：用户时区使用 IANA 标识（如 `Asia/Shanghai`），不使用固定 UTC 偏移。

**TIME-009**：用户跨时区时，DayKey 按新时区的本地时间计算；不追溯修改历史记录；可能在极端情况下出现“同一天重复”或“跳过一天”，应用应提示而不是偷偷修补。

**TIME-010**：夏令时切换日可能只有 23 小时或 25 小时；按日历天计算 `elapsedDays`，不按 24 小时整除。

**TIME-011**：如果切点时刻在夏令时跳变中不存在（例如 02:30），使用跳变后的第一个有效时刻；该规则必须写死并测试。

### 9.3 设备时钟偏差

**TIME-012**：在线时以服务端时间为准；离线时允许使用设备时间，但在同步时必须以日志中的 `at` 与 `dayKey` 对账。

**TIME-013**：日期级调度对分钟级时钟偏差不敏感；但如果用户在切点前后学习，应用应显示“本次学习计入哪一天”，避免争议。

## 10. 验收场景

以下场景使用一个**测试策略 T1**，以便得到确定结果：

- 初始：认识 → S=10 天；模糊 → S=3 天；忘记 → S=1 天。
- 复习：认识 → S×2；模糊 → S×1.2；忘记 → S=1。
- 间隔 = S（四舍五入），clamp 到 [1, 365]；目标保留率不参与 T1 的简化计算。
- 忘记固定次日到期。

| 编号 | Given | When | Then |
|---|---|---|---|
| S01 | 新词，day 0 | 计划内首次点“认识” | `dueDay = 10`；`reps = 1`；新学计数 +1 |
| S02 | S01 之后同一天 | 同日重复再点“认识” | `dueDay` 仍为 10；长期状态不变；只写 `same_day_repeat` 日志 |
| S03 | 新词，day 0 | 首次点“模糊” | `dueDay = 3`；进入同日队列；当天至少再出现 1 次 |
| S04 | S03 之后同一天 | 重复时点“认识” | `dueDay` 仍为 3；该词完成当天复习；长期状态不变 |
| S05 | 新词，day 0 | 首次点“忘记” | `dueDay = 1`；`lapses = 1`；当天至少出现 2 次 |
| S06 | S05 之后同一天 | 重复时点“认识” | `dueDay` 仍为 1；完成当天复习；`lapses` 不再增加 |
| S07 | 到期词，原 `dueDay=10`，实际 day 13 才复习 | 点“认识” | `elapsedDays = 13`（不是 10）；状态按 13 天计算；日志记录真实值 |
| S08 | 到期词，day 10 | 在“历史回顾”里点“认识” | 长期状态不变；`dueDay` 仍为 10；仍进入当天计划 |
| S09 | 到期词，day 10 | 先在历史回顾评分，再在计划内评分 | 只有计划内那次更新状态；历史回顾只写日志 |
| S10 | N=100，到期复习 80，新词 50 | 生成计划 | 复习 80，新学 20；总 100；理由正确 |
| S11 | N=100，到期复习 120，新词 50 | 生成计划 | 复习 100，新学 0；积压 20；预测显示 |
| S12 | 分开模式 R=50，M=30；到期 80，新词 50 | 生成计划 | 复习 50，新学 30；总 80 |
| S13 | N=100，到期 60，未来 100，`fill` | 生成计划 | 复习 100（其中 40 个提前）；标记 `advanced=true` |
| S14 | N=100，到期 60，未来 100，`by_plan` | 生成计划 | 复习 60，新学 40（若有新词） |
| S15 | 到期词已标记“熟知” | 生成计划 | 不出现在复习池；不计入预测 |
| S16 | 已学词被删除后重新加入 | 生成计划 | 按新词处理；无记忆状态；新学池 |
| S17 | 切点 04:00，day 0 的 02:00 | 学习 | 记为 day 0；属于前一天 |
| S18 | 切点 04:00，day 1 的 05:00 | 学习 | 记为 day 1；新的一天 |
| S19 | N=100，已复习 30 后改为 50 | 重算计划 | 已完成 30 保留；未开始的复习目标补到 50；新学目标相应调整 |
| S20 | 计划完成后追加 10 个新词 | 学习 | 立即进入 `extra`；不受 N 限制；预测复习量上升并显示 |
| S21 | 同一天多次重放全部日志 | 重建状态 | 状态哈希与原始一致 |
| S22 | 用户从 Asia/Shanghai 切换到 Europe/London | 跨天 | 按新时区计算 DayKey；历史 DayKey 不变；写时区变更日志 |
| S23 | `allowVagueComplete=false`，首次“模糊” | 同日重复点“模糊” | 仍不能完成当天复习；继续留在队列 |
| S24 | `allowVagueComplete=true`，首次“模糊” | 同日重复点“模糊” | 可完成当天复习；`dueDay` 仍按首次模糊的短间隔 |
| S25 | 策略返回 `intervalDays = 0` | 评分 | 引擎拒绝，回退到 1 天；记录策略错误 |

## 11. 非功能需求

| 类别 | 要求 |
|---|---|
| 确定性 | 相同日志 + 配置 + 策略版本 ⇒ 相同状态；禁止隐藏随机与系统时间 |
| 可重放 | 任意时刻可从日志重建状态；快照可丢弃 |
| 幂等 | 重复命令不重复计数；事件 ID 去重 |
| 性能 | 10 万 Item 的用户，生成每日计划应在 200 ms 内（中端设备）；预测 30 天应在 500 ms 内；具体目标由实现方压测确定 |
| 存储 | 状态与日志分离；日志只追加；支持压缩与归档 |
| 离线 | 核心调度不依赖网络；同步是适配器职责 |
| 隐私 | 不存储单词内容；日志不含 PII；导出/删除可按用户执行 |
| 可移植 | JSON / CBOR 等开放格式；不绑定特定数据库 |
| 可测试 | 每个业务规则有对应场景；策略有黄金测试向量 |
| 可观测 | 计划生成、评分、迁移均有结构化日志；错误可定位 |
| 版本化 | 数据 schema、策略、行为规则均带版本；升级有迁移说明 |

## 附录 B：参考算法的最小公式

以下只给出参考策略 R1 所需的最小骨架，完整公式与参数以选定 FSRS 版本的公开文档为准。

**可提取性**

```
R(t) = 0.9 ^ (t / S)
```

- `t`：距上次计划内评分的天数（实际值）
- `S`：稳定度（天），`R(S) = 0.9`

**下次间隔**

```
I = round(S * ln(targetRetention) / ln(0.9))
I = clamp(I, 1, maxIntervalDays)
```

- `targetRetention` 默认 0.9
- 参考产品记忆卡 MMX-5 使用 0.85；背单词产品未公开当前值

**评分映射**

| 引擎 | FSRS grade |
|---|---|
| 忘记 | 1 Again |
| 模糊 | 2 Hard |
| 认识 | 3 Good |
| 熟知 | 终止，不进入公式 |

**失败处理**

- 参考产品可见行为：忘记后次日到期；本文用 `dueDay = 今天 + 1` 实现。
- 策略仍需更新稳定度 / 难度；具体公式按 FSRS 版本。

**为什么不在本文写死参数**

- 参数会随数据与版本变化；
- 业务规则不应依赖某组参数；
- 只要策略满足“评分 → 状态 → 间隔”的接口，就可以替换。
